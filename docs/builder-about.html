About Builder

Builder composes illustrations from a fixed visual language rather than drawing them. Four modes are four ways into that language, not four tools. This page says what the language is, where it came from, and which parts are real.

Why one engine and not four tools

Four separate builders would produce four families, and the point of a library is that its artwork looks like it came from one place. So the geometry, the single stroke, the color slots and the checks are shared, and a mode only changes which dials it starts on and which slots it lets you bind. Windows and Product UI are the same machine at different settings, which is worth saying plainly rather than hiding behind two buttons.

The standing rule, inherited and not negotiable: adapt, do not invent. Pick the nearest of the twelve layouts, keep its geometry, change only the content. Every tool that follows this produces the same family. Every tool that composes from scratch drifts. Builder enforces it by having no way to move a coordinate, and the one place it lets you out of that is marked.

The four modes

What each one is for, and how much of it is real today.

Windows Working The twelve layouts at Windows settings: neutral grays, a wider corner radius, a quieter shadow, Windows blue as the accent. The preset is a first pass at the dials and not an agreed style, which is the thing to argue with.
Pieces Working Every glyph position in a layout is a named slot. Bind a slot to anything in the library or to one of your own pieces. Free placement sits underneath as an escape hatch, and the checks mark anything composed that way.
Product UI Working The ported exploration, unchanged except that the glyphs are our System Icons. This is the reference the other three are built from, because it is the one that has been proved.
Devices Working A device is a frame with a screen, and the screen takes anything that draws on the 160 grid. A composition built in any other mode goes inside a laptop, and retheming comes along for free.

Where the language came from

The visual language is ported from a product illustration generator exploration rather than invented here. That exploration had already answered the questions that cost the most to get wrong: how many layouts, what a stroke is allowed to be, which slots a palette has, and how to tell a composition from a screenshot. Builder is the interactive front end for it, so the answers stay in one place.

The geometry and the primitives came across verbatim. This style is sub-pixel work: a stroke of 1 where a preset says 0.5 is visibly wrong, so nothing in it is a judgment call to revisit while adding a layout. What did change is the glyphs. The exploration drew around a general purpose icon set; a Windows illustration should be built from Windows marks, so every glyph here is an Expressive Assets System Icon.

The rules that do the work

Five of them, and every check in the tool exists to enforce one.

  • One strokeEvery stroked element uses the preset's single width, currently 0.5 in all three, in var(--il-line). There is no second width and no second color. Separators are filled rects 0.5 tall, not strokes. Icons are filled paths and are never stroked. Hierarchy comes from fills, opacity and the one shadow.
  • One canvasviewBox="0 0 160 160" at whatever size it is shown, with no width or height on the root and no background rect. The outer 10 units are shadow bleed, and the fade runs from y 112 to y 131, so nothing that carries meaning goes below y 112. That is what caps the row count in every repeating layout.
  • One shadowAt most one element casts a shadow: the floating one. Small objects take dy 2 at blur 2.6, anything above about 2,600 square units takes dy 4 at blur 5. A composition nested into a device screen goes flat, because a screen is emissive and a drop shadow inside one reads as dirt.
  • One gradientThe base panel's vertical gradient. No blur, glow, gloss, bevel or perspective anywhere. A device carries two, its own and the one in the view on its screen, and the checks say so rather than failing it.
  • Grayscale firstColor is a guest. The accent marks exactly one of success, selection, active state, a live connection or the primary action, it touches at most two elements, and it never touches structure. If removing color destroys the meaning, the composition was doing too little work.

The presets, and what a preset may move

A preset is a set of token values plus the four dials below. Nothing else in the language changes, which is what lets one engine serve two looks. Adding a preset is adding values and a note on which dials it moves; it is not adding code.

The thirteen token slots

Every color in every primitive is written var(--il-token, #fallback) with the active preset's light value as the fallback, so a file works standalone and still themes when it is inlined in a page. Three relationships matter more than the values: canvas to panel must be visible but quiet, panel to surface is the only real step, and the placeholder bars stay neutral even when the surfaces are warm. That last mismatch is what makes the bars read as content rather than as chrome. The values below are the Soft Layered preset; Windows and Flat outline move the same thirteen.

The five devices

A device is contained: closed on all four sides, with no fade, because a device is a thing rather than a view with more below it. The screen rectangle is the whole contract, so anything that draws on the 160 grid nests into it.

Slots, and adding your own pieces

Pieces mode turns every glyph position in a layout into a named slot. Binding a slot puts real library artwork into a composition without letting the composition itself move, which is the difference between piecing something together and drawing it. The feature glyph, the row leader, the row glyph, the tiles, the second chip, the action glyph and the three matrix columns are all bindable, and which of them a layout offers is in the table above.

Anything bound has to be a monochrome glyph: a single currentColor path, or several, on its own grid. System Icons already are. Anything carrying its own colors is refused rather than recolored, because a tinted brand mark repainted with --il-stroke is a lie about the artwork.

Your own pieces load from an optional file beside this one. The contract is deliberately small: drop the SVGs anywhere under docs/ and list them in builder-parts.json.

{
  "parts": [
    { "id": "plate.rounded", "name": "Rounded plate", "path": "parts/plate-rounded.svg" },
    { "id": "glyph.window",  "name": "Window glyph",  "path": "parts/glyph-window.svg" }
  ]
}

No file means the My pieces tab says so and nothing breaks. The ids are yours and are not validated against anything, because these are not library assets yet: when a piece is good enough to keep it should go through the normal import rather than living in a JSON file next to a tool.

Not built yet

Stated here rather than implied by absence, because a shell that looks finished is worse than one that says what it is.

  • Windows illustrations, as artwork rather than as a presetMode one is the twelve layouts at Windows settings. That is a real thing and it is not the same as the WDS illustration set, which is scenes and objects rather than UI abstractions. Deciding whether those need their own parts vocabulary waits on the illustration intake and an agreed interim style.
  • Composing from library parts, not glyphsA slot takes a whole asset used as a glyph. The point of the structural IDs is that an asset can supply a part, so a card could hold a real plate and a real glyph rather than a placeholder bar. That waits on the anatomy vocabulary settling.
  • Portrait compositionsThe tablet and the phone crop a square composition rather than showing one built for them. Portrait layouts would be new entries in the twelve, which is a decision about the taxonomy and not a quick addition.
  • Color roles instead of token slotsThe thirteen --il-* slots are the exploration's palette model. Expressive Assets already derives group and member color IDs per asset. Those are two answers to one question, and the second one is ours. Reconciling them is a real decision, not a mapping, and it is entangled with the Bridge naming question.
  • Sets, not single illustrationsLayout reuse across a set is what makes a family read as designed. The contact sheet shows the twelve, but Builder cannot yet hold a named set, budget layout reuse across it, or tell you that the fourth illustration is the third header card.
  • Writing backNo output lands anywhere. An illustration built here is a download. Getting it into assets/ means a slug, a meta.json, provenance marked as generated rather than received, and the manifest and validate steps passing. None of that is wired, on purpose: nothing should enter the library through a browser.
  • FigmaA flat export pastes into Figma correctly today, which is why the flat buttons exist, but that is a clipboard, not a pipeline.
