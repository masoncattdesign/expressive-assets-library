Expressive Assets System Map

One library of icons and illustrations, one machine-readable contract, and the tools that read it. This is what exists today, how the pieces hand off to each other, and what is still open.

3,280 assets 8 collections 15,470 drawings as of 4 Sept 2026 head 1d5c05c3

In one paragraph

Artwork is designed in Figma. A reviewed plan file says exactly which Figma nodes become which assets, an importer pulls them down and normalizes them, and every asset lands in assets/ as flat SVG files plus a meta.json describing itself. A build step walks that tree once and writes manifest.json. Everything downstream, the Gallery, the Customizer, and anything we build later, reads only the manifest. That single rule is what keeps the tools from growing private knowledge of how the folders are arranged.

The pipeline, stage by stage

These are numbered because they really are a sequence: each stage only runs on the output of the one before it, and each one is a separate command so a bad step can be rerun without redoing the rest.

01

Survey the Figma file

Reads the source file and lists every page, frame and component with its node id and size set. Nothing is written yet. This is how we find out what is actually in the file rather than what we assume is in it.

npm run figma:survey
02

Write and review a plan

The plan is a checked-in JSON file mapping Figma node ids to asset ids, collections, themes and sizes. It is reviewed by a person before anything is imported, so an import is repeatable and reviewable instead of a one-off script run.

figma-plan.json, and two more
03

Run the import

Renders the planned nodes through the Figma API in batches of 60, cleans each SVG, rewrites monochrome fills to currentColor, namespaces ids, and writes artwork plus a meta.json per asset. Placeholders it replaces are retired.

npm run figma:run:product
04

Derive and tokenize

Fills the gaps Figma cannot. Filled file icons are derived by luminance, illustration themes are derived by contour, and six brand colors are swapped for var(--ea-*) roles so illustrations can be retinted without touching logo colors.

derive-filled, derive-illustration-themes, tokenize-illustrations
05

Build and validate

Walks the tree once, writes third-party notices, emits manifest.json, then validates every record against the JSON schema and fails loudly on a broken path or an unknown theme. One command, four steps.

npm run build
06

Consume

The Gallery and the Customizer fetch the manifest at load and work from it. Adding a collection or a theme to the library needs no change in either tool, because both were written against the contract rather than the folders.

docs/index.html, docs/customizer.html

The contract

manifest.json is the only file a consumer is allowed to read. Every asset appears as one record that says what it is, which themes and sizes exist, where each drawing lives, and whether it can be retinted. If it is not in the record, a tool cannot depend on it.

{
  "id": "product.access",           // collection.name, stable, the address
  "type": "icon",                   // icon | illustration
  "collection": "product",
  "status": "published",            // draft | published | deprecated
  "themes": ["standard", "outline", "filled"],
  "sizes": [16, 20, 24, 28, 32, 48],
  "colors": { "primary": "#0078D4", "secondary": "#8764B8" },
  "recolorable": true,              // true when a non-standard theme exists
  "variants": {                     // per theme, per size, never guessed
    "outline": { "16": "assets/icons/product/access/outline-16.svg", ... }
  },
  "figma": { "fileKey": "l752...", "nodeId": "500631:7859" }
}

Three rules hold this together. Artwork is stored per size rather than scaled at runtime, because a 16px icon is a different drawing and not a shrunken 48px one. Themes are a fixed vocabulary of standard, outline and filled, so a tool can reason about them. And monochrome themes are written in currentColor or var(--ea-role, #hex), so tinting is a CSS decision made by the consumer, not a file we have to ship twice.

The three tools

The tools split by verb. You look things up in one, change how they look in another, and later compose new illustrations in a third. Gallery and the Customizer cover the whole library. The Builder is an illustration tool specifically, and it is not on the critical path right now.

ToolWhat it doesState
Gallery Browse and search the whole library, filter by collection, theme and size, preview against light and dark surfaces, and copy or download a drawing. Each asset links straight into the Customizer. Running
Customizer Pull any asset out of the library and retint it live: accent colors, surface, the --ea-* roles. Answers the question a designer actually asks, which is what this looks like in my theme. Running
Builder Compose illustrations from a kit of reusable pieces rather than drawing each scene from scratch. Not an icon tool. It waits on the illustration cleanup and an agreed illustration style, because there is no kit to build from until those exist. Later
Bridge The separate naming and semantics system. It already has an icon schema with an anatomy block, so the long-term shape is that Bridge names the parts and Expressive Assets provides the drawings. Adjacent

Anatomy, the layer being added nowIn progress

Today the smallest addressable thing is a whole asset. Anatomy makes the parts inside an asset addressable, which is what lets someone say "put a two pixel stroke on the base of every product icon" and have it mean something. A part is a set of shapes that share a color ramp, not a contiguous region, which is why the two head circles in the Teams icon belong to the base below them. This work is about icons: it feeds the Customizer and the naming grammar, not the Builder.

The 12 icon pilot proved this works on real artwork. Parts are marked in the SVG with data-part, so the drawing stays a valid standalone SVG and anything that ignores the attribute still renders correctly. The open question is ownership: if a designer re-exports an icon from Figma, who reapplies the part names.

Open decisions

These are the things that need an answer from a person rather than more code, listed with the cost of getting them wrong.

  • Naming 2,728 of 3,280 ids carry a hyphen inside a name segment, which Bridge's grammar does not allow. Either the ids change or the grammar does, and the longer we wait the more expensive the rename gets.
  • Publishing Everything is published, on the bar that the artwork was received rather than generated here. That bar says nothing about whether a drawing is any good, and there is no review step behind it yet. deprecated also has no process: no asset has ever been retired, so the path has never been walked.
  • Figma sync Writing assets back into a Figma file has to be a plugin, since the REST API cannot write file content. The policy question comes first: on a conflict, does the library overwrite, skip, or flag for review.
  • Anatomy owner Whether part names live in the Figma layer names, in the repo, or in Bridge. This decides who reapplies them on every re-export.
  • Illustrations A separate track from the icon work. The illustration sets need a cleanup and organizing pass, and then an interim style with real guidelines to draw against while the long-term direction settles. The Builder sits at the end of that track, not at the front of it.
  • Third party The 3P page holds roughly 70 third-party trademarks. It stays unimported until someone signs off on the licensing.
